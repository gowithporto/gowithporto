# 02 — Product and User Experience

> **SDLC stage:** 2. Product / UX
> **Status:** PARTIAL — built and documented; no accessibility audit, no validation with real users
> **Baseline:** commit `3eb178a`, 2026-08-16
> **Update when:** a user-facing flow changes shape.

---

## 1. Design principles

Four rules, each traceable to a constraint in `01-PRODUCT` §6.

**Phone first, literally.** The primary persona (P1) is standing in a street in
Porto holding a phone, possibly on mobile data, possibly in sunlight. Every flow
must complete at 375 px. The fulfilment confirmation flow is phone-*only* by
design — it is never used at a desk.

**Never lose the visitor's language.** A visitor who switches to French and then
loses it on the next click has been told the localisation is decorative. This was
a real defect — nearly every internal link hardcoded an unprefixed path — and it
was fixed structurally rather than page by page, with a `LocalizedLink` component
that makes the correct behaviour the default (see §5.2).

**No dark patterns around money.** The AI planner states the credit cost before
generation, not after. Cart totals do not hide fees. The seller is not paid before
the buyer confirms receipt. This is a product principle with an architectural
consequence — see `04-DOMAIN` §4.

**Different audiences get different surfaces, not different permissions on one
surface.** Buyers, store owners and the operator each have a separate area with
its own layout, navigation and guard. A store owner never sees an admin control
greyed out; the route does not exist for them.

## 2. Information architecture

Four route trees, each with its own layout and access rule. Customer-facing routes
are locale-prefixed (`/fr/shop`); the two internal portals are English-only and
excluded from the locale proxy.

```
PUBLIC  (no account; locales en · fr · es · pt)
├── /                          home — hero, categories, discover, experiences, bike banner
├── /shop                      product grid
│   ├── /shop/category/[c]     category filter
│   └── /shop/[slug]           product detail — gallery, variants, add to cart
├── /attractions               attraction grid, category sidebar
│   └── /attractions/[slug]    detail — history, highlights, nearby hotels/restaurants, map
├── /local-experiences         experience grid, duration + category filters
│   └── /local-experiences/[slug]
├── /bike-rentals              provider directory → Google Maps
├── /cart                      line items, pickup vs delivery
├── /checkout                  address, order review → Stripe
│   ├── /checkout/success      order confirmation
│   └── /checkout/cancel
├── /ai                        itinerary planner form
│   ├── /ai/result             generated itinerary
│   ├── /ai/success            credit purchase confirmed
│   └── /ai/cancel
├── /about  /faq  /contact  /privacy
└── /fulfill/[token]           handover confirmation — tokenised, no account

BUYER  (Google sign-in)
└── /dashboard                 credits, recent orders, CTAs
    ├── /dashboard/orders      per-item status, QR codes, report-an-issue
    ├── /dashboard/ai-history  past itineraries
    ├── /dashboard/favorites   saved items across all four content types
    ├── /dashboard/transactions credit purchase history
    └── /dashboard/profile     name, avatar

STORE OWNER  (store code + password)
└── /store-owner               sales chart, summary
    ├── /store-owner/orders    incoming orders, dispatch / ready-for-pickup actions
    ├── /store-owner/products  own catalogue
    │   ├── /new  ·  /[id]/edit
    └── (Stripe Express onboarding + payout dashboard, hosted by Stripe)

OPERATOR  (email + password, role ADMIN)
└── /admin                     KPI overview, sparklines, donut
    ├── /admin/orders          all orders, item drill-down
    ├── /admin/disputes        reported issues, resolution actions
    ├── /admin/stores          stores, commission rate, Connect status
    ├── /admin/users           user list, credits, roles
    ├── /admin/revenue         commission vs payouts, per-store breakdown
    ├── /admin/attractions  ·  /admin/local-experiences  ·  /admin/bike-rentals
    └── /admin/ai-settings     model and prompt configuration
```

### 2.1 Why the fulfilment page sits in the public tree

`/fulfill/[token]` is reachable without any account. This is deliberate: the person
confirming a handover is a courier or counter assistant, not a platform user, and
requiring them to register would guarantee the flow is skipped and settlement never
fires. The token is unguessable and single-purpose, and the action is additionally
gated on a store PIN. The security reasoning is in `07-SECURITY` §4.

## 3. Primary user journeys

### J1 — Visitor plans a trip (persona P1)

```
Lands from search on /attractions/[slug]
  → sees "Plan your trip with AI" call-to-action
  → /ai — fills days, dates, budget, group size, travel styles, interests
  → not signed in? Google sign-in, returns to the form with input preserved
  → submits
      ├─ first generation ever        → free, generates
      ├─ credits remaining            → consumes one, generates
      └─ no free try, no credits      → locked state → credit purchase → Stripe
                                        → /ai/success → back to the form
  → /ai/result — day-by-day itinerary, saved automatically
  → itinerary persists in /dashboard/ai-history
```

Two decisions worth noting. **The free try is not gated behind a card**, because
demand is unvalidated and a card wall at first contact would remove the only
evidence the product can generate. And **generation happens before charging** —
a Gemini failure used to burn the user's only free try, which was both a defect
and a trust problem (FR-15).

### J2 — Visitor buys a souvenir (P1)

```
/shop → /shop/[slug] → select variant → add to cart
  → /cart → choose pickup or delivery
  → /checkout → address (delivery only) → order review
  → Stripe Checkout (hosted; no card data touches the platform)
  → /checkout/success — order shown immediately via /api/orders/confirm
  → confirmation email
  → /dashboard/orders — per-item status and, once dispatched, a QR code
```

### J3 — Handover and settlement (P1 + fulfilment handler)

The system's most distinctive flow, and the one that makes the money model work.

```
Store owner marks the item dispatched (delivery) or ready for pickup
  → buyer receives email; QR code becomes active in /dashboard/orders
  → at handover, handler scans the buyer's QR → /fulfill/[token]
  → handler enters the store fulfilment PIN
      ├─ correct → item marked delivered / picked_up
      │            → seller's share transfers via Stripe
      │            → delivery fee transfers, once per order
      └─ wrong / expired token → generic failure, no information leaked
  → alternatively, the buyer reports an issue from /dashboard/orders
      → item frozen as issue_reported, no transfer occurs
      → appears in /admin/disputes for operator resolution
```

The buyer's phone shows the QR; the *handler* scans and enters the PIN. Neither
party can complete the handover alone — the buyer cannot self-confirm delivery of
something they did not receive, and the seller cannot confirm without the buyer's
token in front of them.

### J4 — Store owner sells (P3)

```
Login with store code + password → /store-owner
  → Connect not onboarded? persistent prompt → Stripe Express (hosted)
  → /store-owner/products → add product with variants, images, category
  → order arrives → /store-owner/orders
  → per item: mark dispatched (with ETA text) or ready for pickup
  → money arrives after buyer confirmation
  → "View My Payouts" → Stripe Express dashboard (real payout dates, hosted by Stripe)
```

Payouts deliberately hand off to Stripe's own dashboard rather than being
reimplemented — see `01-PRODUCT` §7.

### J5 — Operator resolves a dispute (P4)

```
/admin/disputes → item with buyer's reason code and note
  → choose an outcome:
      seller_fault → full item refund to buyer; delivery fee refunded only on
                     single-item orders (BR-9); nothing to the seller
      buyer_fault  → seller receives their share; delivery fee stays with seller
      split        → operator sets buyer % and seller %; platform keeps the remainder
  → Stripe refund and/or transfer execute with idempotency keys
  → item marked resolved; a second resolution is rejected before any Stripe call
  → both parties emailed
```

## 4. Interaction states

Every list and detail surface must define four states. Coverage at baseline:

| Surface | Loading | Empty | Error | Offline |
|---|---|---|---|---|
| Product / attraction / experience grids | Yes | Yes | Route error boundary | Global banner |
| Cart | n/a — client state | Yes, with CTA to shop | n/a | Global banner |
| AI planner | Yes — generation can take seconds | n/a | Inline; 429 renders as "high demand" | Global banner |
| AI result | Yes | n/a | Route error boundary | Global banner |
| Buyer orders | Yes | Yes, with CTA | Route error boundary | Global banner |
| Favourites | Yes | Yes, per content type | Route error boundary | Global banner |
| Store-owner orders | Yes | Yes | Route error boundary | Global banner |
| Admin tables | Yes | Yes | Route error boundary | Global banner |
| Fulfilment confirmation | Yes | n/a | Inline, deliberately generic | Global banner |

Global mechanisms:

- **`app/error.tsx`** — branded route-level error boundary with a retry action.
- **`app/global-error.tsx`** — last-resort boundary for failures in the root layout.
- **`app/not-found.tsx`** — branded 404 rather than the framework default.
- **`ConnectivityBanner`** — listens for browser online/offline events, with a
  `/robots.txt` poll as a fallback because the browser event alone reports
  "connected to a network" rather than "the internet works."

**Gap:** these boundaries display a friendly message to the user but report the
error nowhere. There is no error tracking, so a boundary firing in production is
invisible to the operator. See `10-OPERATIONS` §4.

## 5. Localisation behaviour

### 5.1 Model

Four locales: `en` (default, unprefixed), `fr`, `es`, `pt`. Two layers:

- **UI chrome** — flat JSON dictionaries in `src/i18n/{en,fr,es,pt}.json`, read
  through `t(lang, key)`.
- **Catalogue content** — a `translations` sub-document on `Product`,
  `Attraction` and `LocalExperience`, keyed by locale, with per-field overrides
  falling back to the base field. This means a partially translated item degrades
  to English on the untranslated fields rather than rendering blank.

`src/proxy.ts` (Next.js 16's rename of the `middleware.ts` convention) detects the
locale prefix, rewrites to the unprefixed route, and passes the locale through a
request header. The root layout emits `hreflang` alternates and a dynamic
`<html lang>`.

Adding a fifth locale is one JSON file plus one line in `src/i18n/index.ts`.

### 5.2 The locale-loss defect, and why the fix was structural

Switching to French and clicking any internal link returned the visitor to English.
Root cause: nearly every `<Link>` in the application hardcoded an unprefixed path,
so the URL — the source of truth for locale — was discarded on navigation.

The fix was not to prefix 33 files' worth of links by hand and hope. A
`LocalizedLink` component was introduced as a drop-in replacement for `next/link`
that prefixes internal hrefs with the active locale automatically, and adopted
across every customer-facing file. **The correct behaviour became the default, so
the defect cannot recur through ordinary carelessness.** A related instance —
five dashboard pages hardcoding `redirect("/")` on logged-out access — was fixed
the same way, via `src/lib/localePath.ts`.

This is the general pattern preferred throughout the codebase: when a class of bug
appears more than twice, change the shape of the code so the bug is unavailable,
rather than fixing the instances.

### 5.3 Deliberate non-translation

Budget, group-size and travel-style **values** stay in stable English
(`"Cheap"`, `"Culture & History"`) because `promptBuilder.ts` interpolates them
directly into the Gemini prompt. Only the displayed label is translated. Translating
the value would silently change the prompt the model receives, in a way no test
would catch.

### 5.4 Known localisation gaps

- UI chrome on shop, attractions, local-experiences, cart, checkout and dashboard
  still renders hardcoded English labels and filters. Catalogue *content* on those
  pages is translated; the surrounding furniture is not.
- Product `variants[].name`, attraction `nearbyHotels`/`nearbyRestaurants` blurbs
  and `Category`/`BikeRentalProvider` names are untranslated — deliberately
  deferred to keep the 2026-08-13 pass shippable in one day.
- The authenticated dashboard has never been visually checked in all four
  languages while logged in. Code review found no session-dependent branch, but
  that is reasoning, not evidence.

## 6. Responsive behaviour

Tailwind's default breakpoints; mobile is the base layer and desktop the
enhancement, not the reverse.

| Viewport | Behaviour |
|---|---|
| < 640 px | Single-column grids; hamburger navigation; filter sidebars collapse to a sheet; admin and store-owner tables scroll horizontally rather than reflow |
| 640–1024 px | Two-column grids; sidebar navigation appears in the internal portals |
| > 1024 px | Full grids; persistent sidebars; ad rails on the AI result and dashboard pages |

The hero section and header navigation were rebuilt after locale routing
introduced wrapping and logo drift on small screens — longer French and Portuguese
strings exposed layout that had only ever been tested against English. **A
localisation change is a layout change**, and is now treated as one.

**Gap:** admin and store-owner tables are usable but not pleasant on a phone.
Accepted — persona P4 operates from a desk, and P3 manages products from one.

## 7. Accessibility — an honest position

**NFR-8 targets WCAG 2.1 AA. It is not met, and no audit has been run.**

What is in place, mostly as a by-product of good defaults rather than deliberate
work: semantic HTML through Next.js and standard elements; `alt` text on carousel
imagery, including translated `alt` strings; keyboard-operable native form
controls; a dynamic `<html lang>` that gives screen readers the right pronunciation
per locale.

What has never been verified: colour contrast across the brand palette — the
warm-on-warm scheme is the most likely failure; focus visibility on custom
components (`Button`, `Select`, `SingleImagePicker`); keyboard traversal of the
mobile hamburger and the filter sheets; screen-reader labelling of icon-only
controls; whether the QR-code handover flow has any non-visual alternative.

That last point is the one that matters most. **If a blind buyer cannot present a
QR code, they cannot complete a handover, and their money stays in escrow.** This
is a functional exclusion, not a cosmetic one, and it has no workaround in the
current design. A PIN-visible-to-buyer fallback is the obvious remedy and is
recorded in `TODO.md`.

Planned first pass, in order of cost-to-value: automated axe-core scan of the ten
highest-traffic routes → contrast audit of the palette in `STYLE_GUIDE.md` →
keyboard traversal of the checkout and fulfilment paths → a non-visual handover
alternative.

## 8. UX validation — an honest position

**No usability testing has been conducted with any real user.** No moderated
sessions, no unmoderated tests, no analytics, no session recording, no A/B tests.

What has informed the design instead: the founder's own use of the product,
screenshot review that surfaced real defects (the locale-loss bug in §5.2 was
found this way), and comparison against comparable travel and marketplace
products.

Everything in this document describing what a user will do is therefore a
**hypothesis**, not a finding. The cheapest useful correction — five moderated
sessions with actual Porto visitors, which is enough to surface the majority of
severe usability problems — costs nothing but access, and access is the one
resource a founder living in Porto has. It has not been done. It should be, before
the launch gate in `01-PRODUCT` §9.3 is judged complete.

## Trade-offs recorded

**Separate portals over one role-aware interface.** Three layouts, three
navigations and three guards is more surface than a single interface with
conditional rendering. It was chosen because conditional rendering by role is a
recurring source of authorisation defects — a control hidden in the UI but not
guarded on the server is the classic failure — and because each audience's mental
model is genuinely different. The cost is real duplication in layout and table
code, and it is accepted.

**Tokenised handover over an account for handlers.** Requiring couriers and shop
staff to hold accounts would be more auditable and would let the system attribute
a confirmation to a named person. It would also guarantee the flow is skipped in
practice, which means settlement never fires and the escrow model collapses. The
platform accepted weaker attribution — store-level PIN rather than per-person
credentials — in exchange for a flow that a stranger will actually complete in
fifteen seconds on the pavement. Revisit if false confirmations ever appear
(`07-SECURITY` §4).

**Shipping four locales before validating one.** Localisation was built for an
audience that does not yet exist, and consumed several working days that could
have gone to tests or monitoring. The defence is that SEO in four languages is the
only acquisition channel available with no budget (C-5), and retrofitting locale
routing into an established URL structure is far more expensive than building it
in. The defence is honest but not conclusive.
